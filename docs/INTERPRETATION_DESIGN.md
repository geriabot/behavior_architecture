# Interpretation: design

Status: implemented on branch `devel` (created as `interpretation`). Sections 1 to 11 are the
design as reviewed; section 12 lists where the implementation departs from it, and why. The
user-facing documentation is in the [README](../README.md#interpretation-optional).

## 1. What interpretation is

The architecture has layers that form the chain of control: deliberation and planning (optional),
coordination (an FSM) and action (Behavior Trees), each with authority over the one below.
*Interpretation* is not one of them. It turns what arrives without structure (a request in natural
language, a line said by a person, a camera image) into a validated answer to a narrow question
that a layer asks: which behavior fits this request, which values of a form this line gives, which
of these detections is the person in red. It commands nothing: the layers consult it, it answers,
and what to do with the answer is always decided by the layer that asked. It is not a capability
either, since it has none of a capability's structure (its own coordination and action, a goal
interface).

Interpretation is drawn as a column beside the layers that consult it, one per level of the
architecture that needs one, optional like deliberation. Behind it is a model (an LLM or a
multimodal model), which is external and replaceable.

Two properties are part of the contract:

- **No state.** Everything a question needs travels with it. A per-request fact that later
  questions reuse (for example a distinctive feature of a tracked person) is kept by the tree or
  the orchestrator, in the blackboard, and passed again. Every question can therefore be logged,
  replayed and tested on its own.
- **No control.** Interpretation never activates, stops or sequences anything, and never decides
  an outcome. It answers; the asker decides.

## 2. What is generic and what is not

Both systems that use the framework today ask a model narrow questions from their FSM and their
trees, and each wrote the same machinery separately. The machinery becomes generic; the questions
stay in each system.

| Generic (in `behavior_architecture`) | Particular (in each system) |
|---|---|
| The query interface: a named question, its context, an optional image, a time budget; a validated answer, whether a fallback was used and why | The questions themselves: their templates, output schemas, validation and fallbacks |
| The server: prompt from a template, structured output, loose JSON parsing, validation, retries, per-call limit and budget, fallback, logging and replay | What a system does with an answer (the behavior logic: filling a form, advancing a quiz, tracking a target) |
| Model backends behind one abstraction (local and cloud, text and image, a model per question) | Which model answers which question (configuration) |
| Choosing a behavior from a catalog: ask, and reject an id that was not offered | Filtering the catalog (by needs, by capabilities) before asking |
| A BT node and an FSM helper to ask without blocking | The trees and FSMs that ask |
| Rule-based answers that take the model's place (for ablations and fallbacks) | Which rules exist (for example "the most centred detection") |

## 3. What is added to the package

Interpretation is a service that the framework provides and launches, not a base class that each
system implements: a system configures it (its questions in YAML, its prompt templates and, only
for questions with logic of their own, a small Python module the server loads) and asks it,
through a helper class in its orchestrator and a BT node in its trees.


Everything is new; nothing that exists is changed (`BaseOrchestrator`, `BehaviorRunner`,
`mission_executor`, `/behavior_status`, the existing launch files and configs keep their current
API and behavior). A system that does not use interpretation builds, links and runs as today.

- `srv/Interpret.srv`, generated by the package (it becomes also an interface package).
- `behavior_interpretation/` (Python; see section 12): the server node `interpretation_server`,
  the question registry, the interpreters and model backends, logging and replay.
- `include/behavior_architecture/interpretation/interpretation_client.hpp` (C++): a non-blocking
  client for orchestrators, by composition (an object the orchestrator owns), with a
  `choose_behavior` helper.
- A BT plugin library `behavior_architecture_interpretation_bt_nodes` with the node `Interpret`
  (a new ID: the systems' own nodes keep theirs).
- `launch/interpretation.launch.py`, and a launch argument `interpretation` (default `false`) in
  the generic launch file, which starts the server when true.
- Tests: gtest for the client and the BT node, pytest for the server with a fake backend.

The C++ code uses only idioms that build on both Jazzy and Lyrical (`target_link_libraries` with
the `_TARGETS` variables, `async_send_request(...).future.share()`), so one commit can be merged
into `main` and `lyrical`.

## 3b. Interpreters

The service is generic: a caller asks a question and does not know how it is answered. Each
question declares in its definition the *interpreter* that answers it: `llm` (a language or
multimodal model, through the backends of section 7; the default and the only one implemented
now), `rule` (deterministic code, such as attention's detection selectors), and, later, others
such as a world model. The server hosts the interpreters as plugins behind one interface
(`answer(question, request) -> answer, source`); adding an interpreter changes neither the service
nor the callers. The answer says which interpreter gave it. A request may later carry an optional
field to force an interpreter, without breaking existing callers.

A question may name a *chain* of interpreters, tried in order: an interpreter may decline a call
("not applicable"), and the next one answers. For example `interpreter: [rule, llm]` with
attention's detection selector: the rule answers only when the only field asked is the id of a
detection, and otherwise declines so that the model answers. The interpreter (or the chain, and
the rule to use) of each question can also be overridden by configuration at launch, without
editing the question's definition (a server parameter per question, or a variant), as attention's
`ablation.detection_selector` requires.

Each system launches its own server, configured at launch (its questions, templates, routes and
interpreters, read from the files and parameters its launch file gives): one interpretation per
level of the architecture, one server per system. The service name is relative, so each server
lives in its system's namespace (for example `/interaction/interpretation/interpret` and
`/attention/interpretation/interpret` on a robot that runs both). A request carries only what
belongs to that call.

## 4. The query interface

```
# Interpret.srv
string question          # registered name, e.g. "choose_behavior", "extract_turn", "identify_target"
string request_id        # who asks (a request, a dialogue): for logging and replay only
string context           # JSON object: what the question's template and validation need
string text              # optional free text (a user's line, a task), also usable by the template
sensor_msgs/Image[] images  # optional, zero or more (a frame, several views, a short
                            # sequence); sent only to questions that use images
float64 budget_s         # time left for this answer; 0 = only the per-call limit
---
bool success             # false only if the question is unknown or the request malformed
string answer            # JSON object, valid against the question's schema (model, rule or fallback)
string source            # the interpreter that answered ("llm", "rule", ...), or "fallback" or "invalid"
string fallback_reason   # why: "timeout", "invalid", "model_down", "budget"
string message
```

`invalid` means that no valid answer came back and the question has no fallback: the asker gets
no answer and decides what to do, which is distinguishable from a valid answer of the model (for
example attention's `-1`, "the target is not there", which starts a search). A question whose
answer is not needed at once (attention's Q5) is asked the same way; the client simply does not
wait for it.

## 5. Declaring a question

A system declares its questions in YAML and, when needed, a small Python class:

```yaml
questions:
  identify_target:
    template: additional_information_with_image   # key in the system's templates file
    fields: ["int:id"]                 # the answer's fields, with the system's own names; or
    fields_from: context.inputs        #   taken from the call's context (fields declared by a
                                       #   behavior of the catalog, as attention's Q3 and Q4)
    choices_from: context.detection_ids   # the answer must be one of these (or -1)
    uses_image: optional               # true, false, or optional (used if the call brings any)
    max_images: 1                      # how many images the question accepts (default 1)
    max_retries: 0                     # per question; 0 = no retry
    fallback: none                     # none (the result is `invalid`) or a value
    interpreter: llm                   # llm (default), rule, ... (section 3b)
    route: behavior_input_with_image   # which backend/model answers (see section 7)
    max_tokens: 50
    variants:                          # selected by configuration, e.g. an ablation
      no_image: {template: additional_information, route: behavior_input, uses_image: false}
```

Fields are typed as `int`, `str`, `float`, `bool` and arrays of these, with the system's own names
(attention's Q2 answers `attention_action_id`, not a generic `id`). From them the server builds
both the schema sent to the backend and an `{output_format}` block that the template can include,
with a formatter the system may supply, so that the prompt a system sends today stays the same
byte for byte.

The optional class can override `build_prompt(context, text)`, `format_output(fields)`,
`validate(answer, context)`,
`fallback(context, reason)` and `answer_without_model(context)` (a rule: when configured, the
question is answered by it and the model is not called, which covers attention's
`detection_selector` and its ablations). Classes are loaded from the modules a system lists in
the server's `question_modules` parameter, like the interaction system's `skill_modules` today.

## 6. The server

One call, step by step: look up the question; if a rule is configured, answer with it; otherwise
build the prompt, call the backend of its route with the structured-output schema (and the image
if the question uses one), parse loosely, validate (schema, `choices_from`, the class's
`validate`), retry a failed or invalid answer up to the question's `max_retries` (0 = none) within
the per-call limit and the budget (`budget_s` = 0 cuts nothing), and fall back, or answer
`invalid` if the question has no fallback. The server keeps no state between calls
(no per-request memory; the model sessions, if a backend uses them, are not conversation history).

Every call is written as one JSON line: question, request id, prompt, image file (saved once),
raw answer, parsed answer, source, fallback reason, latency, tokens and the model version that
answered. A `recorded` backend answers each call from such a log (by question and prompt), which
makes a system's behavior reproducible without a model, and lets two implementations be compared
decision by decision. Each system provides an importer from its current recordings (attention's
`_FOCUS`, `_ACTION` and `_INPUT` files, the interaction system's call logs) into this format, so
that the recordings of finished campaigns can be replayed, and either migrates its evaluation tools
to the new log or exports the log to its old format.

## 7. Model backends

One abstraction, `generate(model, prompt, schema, images, limits) -> text`, with backends for
Ollama, OpenAI-compatible HTTP, Gemini and llama_ros, each translating the schema into its own
dialect (Ollama `format`, OpenAI `response_format`, Gemini `response_schema`), with temperature 0
by default, the per-backend options (`keep_alive`, `num_ctx`, reasoning on or off) and
prompt-prefix caching where the backend offers it.

During the migration the backends reproduce exactly what each current gateway sends, since the
model's answers depend on it: the same schema for the same fields (attention's router: `int`,
`str`, `float`, `bool` and their arrays, `additionalProperties: false`; the interaction system's
gateway: its `format_schema`, `cache_prefix_len` and `think`), and the same image bytes (lossless
PNG, no resizing, base64, in the order given; encodings `rgb8`, `bgr8`, `rgba8`, `bgra8`, `mono8`, `8UC3`). With one image the request is the one sent
today (Ollama: `images: [png]` in the message; OpenAI: the text followed by a single `image_url`
part in `content`, in that order); with none, neither the `images` key nor an `image_url` part. The current
gateways stay in the branches that hold each paper and are retired afterwards. A *route* names a backend and a model; each question names a
route, so different questions can use different models. This merges what the interaction
system's gateway (sessions, caching, providers) and the attention system's router (one route per
question, images, schema dialects) do today.

## 8. Asking from the FSM and from the trees

- `InterpretationClient` (C++), owned by an orchestrator: `ask(question, context, text, images,
  budget)` returns at once; `control_cycle` polls the result, so the FSM never blocks.
  `choose_behavior(question, offered, context)` is the generic mechanism only: it lists the
  offered behaviors into the context, asks the system's own question (its template and its answer
  field, which are part of each system's evaluated method), and rejects an id that was not offered
  as -1 with a reason. Filtering the catalog before asking, and chaining questions (attention asks
  Q2 with Q1's rewriting of the task), stay in the orchestrator.
- `Interpret` (BT node): ports `question`, `variant`, `context` (a JSON string from the
  blackboard), `text`, `images` (a blackboard entry holding zero or more images), `budget_s`,
  `wait` (default true); outputs
  `answer`, `source`, `fallback_reason`. With `wait` true it runs without blocking the tree
  (RUNNING until the answer arrives). With `wait` false it returns SUCCESS at once and writes the
  answer to the blackboard when it arrives, and a node `InterpretationResult` picks it up later
  (attention's Q5, asked once with the image of the Q4 that chose, its answer added to the later
  Q4s). New blackboard keys are prefixed `interpretation_`.

## 9. How the two systems map onto it

- **Attention.** Q1 and Q2 (and the optional needs question) become questions asked through
  `InterpretationClient` from the FSM, Q2 through `choose_behavior` over the catalog the
  orchestrator already filters by capabilities. Q3 and Q4 become `Interpret` nodes, with the plain
  image or the latched detections image as the node's image. Q5 is asked without waiting, and its
  answer is kept in the blackboard and passed to the later Q4s. `send_image=false` is a
  configuration of the question; `detection_selector` is a rule. The logs replace the `_FOCUS`,
  `_ACTION` and `_INPUT` files, with the same content.
- **Interaction.** The choice of the dialogue behavior becomes `choose_behavior` (the filter by
  the material a behavior needs stays in the system). Today each *skill* both asks the model and
  applies the answer to the state of the dialogue. After the change, the skills keep only the
  behavior logic (applying answers, counters, the frame) in a node of the system that no longer
  talks to any model, and every model question goes through `Interpret`. The trees do not change.

## 10. Compatibility and testing

- Additive only, as above; default launch unchanged (`interpretation:=false`).
- Before any merge into `main` or `lyrical`, on both Jazzy and Lyrical: build and run the tests of
  every package that depends on `behavior_architecture` (attention_system, interaction_system,
  dummy_robot), each in a workspace of its own (never in the install space a robot uses).
- Equivalence of each migrated system with its current version: all its unit and system tests;
  the same prompts byte for byte, the same schemas and the same image bytes for the same calls; and
  the replay of recorded model answers (including the recordings of finished campaigns, through
  the importers) through the old and the new implementation, compared decision by decision.

## 12. Implementation notes and deviations

What the implementation adds to, or changes from, sections 3 to 10:

- **Python package name.** The server is the package `behavior_interpretation` (with
  `interpreters/base.py`, `interpreters/rule.py` and `interpreters/llm/`, whose `backends/` hold
  the model backends), not `behavior_architecture/interpretation/`: the Python module generated
  for the interface is `behavior_architecture` (`behavior_architecture.srv`), and a second
  package of that name would collide with it.
- **Interface.** The request has an optional `string variant` (empty: the server's
  configuration), which the BT node's `variant` port fills. `fallback_reason` has one more value,
  `declined`, when every interpreter of the chain declined. A request with more images than the
  question's `max_images`, or with none for a question with `uses_image: true`, is malformed
  (`success` false).
- **Interface target.** The interface is generated with the target `behavior_architecture_interfaces`,
  since `behavior_architecture` is the base library's target. The typesupport dispatch loads the
  libraries of an interface by its package's name, so the generated libraries are given the names
  that a target named after the package would have (`libbehavior_architecture__rosidl_*.so`).
- **Linking is opt-in.** Generating an interface makes rosidl add its libraries, targets,
  include directory and dependencies to the package's default CMake variables, so every package
  that finds `behavior_architecture` (with `ament_target_dependencies()` or with
  `${behavior_architecture_LIBRARIES}`) would link the interface's typesupport libraries, and
  the client too if it were exported the same way. Interpretation is not part of the base, so
  that is avoided: the base's exports are declared before the interface, so that the default
  variables are computed in the same order as without interpretation; what
  `rosidl_generate_interfaces()` adds to the export lists is moved out of them, and the export
  sets of the interface and of the client are installed by the package itself. Two config files
  of the package (`cmake/interpretation-extras.cmake.in`, included first because rosidl's own
  config files expect the interface targets to exist, and
  `cmake/interpretation_dependencies-extras.cmake.in`, included last so that finding the
  dependencies of interpretation does not change the default variables) define the imported
  targets and the variables `behavior_architecture_INTERPRETATION_TARGETS` (the client,
  `behavior_architecture::interpretation`), `behavior_architecture_INTERPRETATION_INTERFACE_TARGETS`
  (the generated interface) and `behavior_architecture_INTERPRETATION_FOUND`. The default
  variables (`_LIBRARIES`, `_TARGETS`, `_INCLUDE_DIRS`, `_DEPENDENCIES`,
  `_RECURSIVE_DEPENDENCIES`) are those of the package without interpretation; a package that
  does not name interpretation gets the same link line and the same shared libraries (checked
  with dummy_robot against the package without interpretation, on Jazzy; on Lyrical the
  variables were compared). The variables `behavior_architecture_TARGETS__<typesupport>` and
  `behavior_architecture_LIBRARIES__<typesupport>` that rosidl defines for interface packages
  are kept; nothing links them unless it asks for them. The BT nodes' library is loaded by name
  and is not exported. How to link it is in the README (Linking interpretation).
- **Interpreters.** A failure (no valid answer) ends the chain; only a decline passes the call to
  the next interpreter. The chain is written `interpreter: [rule, llm]` or
  `"rule:most_centered,llm"`; a variant may set it, and the server parameter
  `interpreter_overrides.<question>` replaces it at launch. Rules and output formatters are
  registered by the question modules (`@rule('name')`, `@formatter('name')`).
- **Choices.** `choices_from` also accepts the values of `choices_extra` (default `[-1]`, "not
  there"); a context entry that is a list of objects contributes their `id`.
- **Dialects.** Each HTTP backend has two dialects: `llm_router` (default; attention's router)
  and `llm_manager` (the interaction system's gateway). The `llm_router` requests of Ollama and of
  OpenAI-compatible APIs, and the PNG images, were compared byte for byte with the router's own
  functions, and the `llm_manager` request of Ollama with the body that the gateway's httpx client
  sends; the `llm_manager` request of OpenAI-compatible APIs has the same parameters as the
  gateway's openai SDK call (the SDK's serialization is not reproduced byte for byte). Gemini's
  `llm_router` dialect is the request of attention's Gemini bridge, image included: converted to
  bgr8, not resized, JPEG at quality 95 by OpenCV, mime type image/jpeg.
  Its `llm_manager` dialect follows the google-genai SDK's request in content only.
- **Token cap.** Attention's router sends no token cap, so `max_tokens` is sent only by the
  `llm_manager` dialects. `cache_prefix_len` is accepted and ignored, as the interaction system's
  gateway does for Ollama, OpenAI and Gemini.
- **Limits.** A route's `timeout_s` (default 120 s) limits each attempt; the budget limits the
  whole call, and an attempt cut by it fails with `budget`. The C++ client's own limit for a
  response (default 120 s) only protects the asker from a server that does not answer.
- **FSM helper.** The helper for orchestrators is `InterpretationClient` itself (its handles are
  polled in `control_cycle`); it accepts any node type (`rclcpp::Node`, a lifecycle node, or a
  pointer to either). `choose_behavior` writes `offered_behaviors` (id, name, description) and
  `offered_ids` into the context.
- **BT nodes.** Besides the ports of section 8, `Interpret` has `request_id`, `service`,
  `timeout_s`, `result_key` and `fail_on_invalid` (default true: FAILURE when the source is
  `invalid`), and a `message` output; the default outputs are `{interpretation_answer}`,
  `{interpretation_source}`, `{interpretation_fallback_reason}` and `{interpretation_message}`.
  `images` is a blackboard entry of type `std::vector<sensor_msgs::msg::Image>`. With `wait`
  false, the blackboard entry (`interpretation_pending_<question>` or `result_key`) holds the
  question in progress, which receives the answer when it arrives; `InterpretationResult` reads
  it (and sends the request then if the server was not up when it was asked).
- **Paths.** The server's file parameters accept `package://<package>/<path>`.
- **Not implemented here.** The importers from each system's current recordings (section 6)
  belong to each system.
- **Tests.** Tests that create ROS nodes run in a ROS domain of their own (ament_cmake_ros) when
  `ROS_DOMAIN_ID` is not set in the environment, and use namespaces of their own otherwise.
